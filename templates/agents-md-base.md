## Module Boundaries

**This is the section a generic setup-command file skips. An agent must read this before creating or modifying any file.**

```
src/
├── modules/
│   ├── [domain-a]/     — owns: [responsibility]. May import from: shared/ only.
│   ├── [domain-b]/     — owns: [responsibility]. May import from: shared/ only.
│   └── [domain-c]/     — owns: [responsibility]. May import from: shared/ only.
├── shared/             — cross-domain utilities. May not import from any module/ directory.
└── database/
    └── migrations/     — every schema change requires a migration file here. No direct ORM sync.
```

**Forbidden:**
- A module importing directly from another module (route cross-domain calls through a defined service interface, not a direct import).
- Business logic inside a controller, route handler, or UI component — it belongs in the service layer.
- Database queries outside the repository/data-access layer.

**Before creating a new file, an agent must determine:** which module owns this responsibility, and does an existing file in that module already handle it? Do not create a new module for something an existing one already owns.

## Data Flow Rules

**Trace this path before writing any endpoint, route, or mutation:**

```
Client request
  → Auth/guard layer (auth check happens HERE, not in the handler body)
  → Input validation (reject malformed input before it reaches business logic)
  → Controller/route handler (thin — delegates immediately, contains no business logic)
  → Service layer (business logic lives here)
  → Repository/data-access layer (all queries live here — no raw queries elsewhere)
  → Database (RLS/row-level checks apply here, not just at the application layer)
  → Response shape (defined once per endpoint — do not vary the shape across similar routes)
```

**An agent must never:**
- Query the database directly from a controller or UI component.
- Skip the validation step because "the frontend already validates it."
- Assume an integration exists without confirming it in this file's Tech Stack or Module Boundaries sections above.
